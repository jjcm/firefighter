# Trust model and operating limits

Firefighter deliberately grants the model autonomous root execution on one Ubuntu host. It polls external intelligence, collects local observations, asks the configured planner for structured actions, records intent before execution, runs commands and verification, and reports outcomes. The harness does not ask for approvals. Its purpose is to shorten response time; it cannot guarantee prevention or complete breach detection.

## Five limits to account for

- **The model can make a damaging decision.** It may misread an advisory, choose an incomplete fix, break a service, or write an unsafe command. JSON validation checks the action contract, not whether a command is correct. Keep an independent recovery path, tested backups, and service-specific verification in operator instructions.
- **Feed prompt injection is not solved by a system prompt.** Posts, advisories, repository content and command output can contain hostile instructions. Firefighter labels these as untrusted and instructs the model to verify facts; that reduces exposure without proving the model will resist every injection. Prefer vendor corroboration, signed packages and checks tied to actual installed software. Do not describe feed text as trusted just because it contains a CVE identifier.
- **Root authority can bypass harness limits.** Command/output limits, a stripped subprocess environment and process-group cancellation constrain ordinary execution. A root command can still read credentials from disk, detach a process, change the daemon, modify logs or contact a remote system. Local-only scope and configured rotation hooks are model policy, not an OS isolation boundary. Keep backup controls and reporting credentials on a separate trusted system when possible.
- **An already compromised host cannot establish its own trust.** A privileged attacker can falsify inventory, suppress evidence and forge or stop local reporting. A clean scan or successful package update does not prove eradication. Preserve available evidence, contain the exposure, then use an external trusted control plane for rebuild and credential revocation when root compromise is plausible. Backups restore state; they do not undo exfiltration or revoke stolen credentials.
- **Coverage and outside services can fail.** Feeds can be incomplete, late or rate-limited; scanners may be absent or miss exploitation; the model/API may fail or refuse a request. API planning sends host observations and retained command output off-host to the configured provider. Credential redaction is best effort and does not recognize every secret. Review provider data handling, avoid commands that dump secrets, and monitor source errors, deferred assessments and report-delivery failures. No report is not evidence that the host is safe.

## Enforced boundaries

The daemon serializes host work, validates structured decisions, bounds rounds, output and command runtime, records decisions/action intent/results, runs explicit verification and available rollback, and retries unfinished assessments. `--observe` executes no model-generated commands, including read-only scans. Autonomous mode has no approval stage.

Reports use a durable outbox and signed requests. The Grok Bot plugin accepts reports only, validates signatures and timestamp freshness, deduplicates accepted event IDs, and invokes a configured reporting routine. It has no inbound command API. HTTP acceptance confirms delivery to the routine, not that the user has read it. Reporting and model outages should remain visible through independent host/service monitoring.
