The process

01

((·)) Listen

The hub polls X and official sources centrally, then broadcasts signed vulnerability notices to every subscriber.

02

⌕ Investigate

Each server’s LLM checks its own versions, exposure, logs, and evidence. A notice is a lead, never a command.

03

⌁ Respond

Apply package or code fixes, test changes, contain exposure, and invoke configured key-rotation hooks.

04

▤ Verify & report

Check the fix and service health. Use rollback when supplied. Keep a local audit and report to Grok Bot.

↳ Shared intelligence. Independent decisions. Remediation runs on your server.

Installation quickstart

One installer. Your model API. A root agent that acts on its own.

This might delete your entire server.

This is an experimental, unproven approach. Faster patching is the bet; being safer is not a proven result. Keep tested, independent backups and read the FAQ.

Before the first installation, you must type this exact sentence in your terminal:

I understand the risks and that this might delete my entire server.

Ubuntu · architecture detected automatically
curl -fsSL https://45.76.243.18/install.sh | sudo bash

Executes the installer as root. It checks download hashes, installs the binary and service, and provisions the shared feed with its pinned public key. Existing configuration is preserved. A new installation stays stopped until you configure your model API and start it.

Hashes from the same server are not independent proof of trust. For advanced key and release verification, see the verification notes (repository access required).

Local configuration · keep credentials off the command line
sudoedit /etc/firefighter/firefighter.env /etc/firefighter/config.json

Set the API credential named by llm.api_key_env in the root-only environment file. Choose your compatible API and model, then configure application paths, health checks, and rotation hooks. The installer supplies the shared notice-feed configuration.

Start autonomous operation · watch the local log
sudo systemctl enable --now firefighter
sudo journalctl -u firefighter -f

Once started, Firefighter runs as root and makes decisions without runtime approval prompts. You own the outcomes. Stop the service with sudo systemctl stop firefighter.

Operational boundary

Runs as root.
Makes changes.
Keeps an audit trail.

The local LLM decides what to investigate and fix. There are no runtime approval prompts. Commands, results, verification, and recovery attempts are recorded locally.

Relevant local observations are sent to your configured model API. Secret redaction is best effort.

A successful patch does not prove a host was never compromised. Backups, independent monitoring, and recovery from a trusted system still matter.
