# Firefighter

An autonomous, API-driven incident-response daemon for **Linux with systemd**, written in Go. It watches vulnerability disclosures, investigates the local host, executes fixes as root, checks the result, and reports to Discord, Telegram, Slack, or Grok Bot. **There are no runtime approval prompts.**

[Public notice board](https://45.76.243.18/) · [FAQ](https://45.76.243.18/faq) · [Source health](https://45.76.243.18/api/v1/status) · [Deployment guide](docs/deployment.md)

The shared hub ingests disclosures once and distributes signed notices to clients. Each client independently inventories its own server, asks its configured model what to do, and performs local remediation. **The hub distributes advisory data only; it has no remote-command channel.** Signatures authenticate the publisher, while notice text remains untrusted input. The hosted hub currently polls Ubuntu notices, CISA KEV, and NVD. Paid X intake is disabled; the integration remains available for an operator to enable later. The board reports current source health.

This is a working initial implementation with fixture-tested execution and recovery paths. It has not been validated against a live compromised production server. A patch or a clean scanner result is never treated as proof that an intrusion did not occur.

## What it does

- **Intake:** a central hub supports X/Twitter recent search, Ubuntu Security Notices, CISA's Known Exploited Vulnerabilities catalog, NVD, and configurable vendor RSS/Atom feeds. Clients verify signed notice batches using a pinned Ed25519 public key. Standalone direct polling is also available. Social disclosures without CVE IDs are included, and intake runs independently of long scans and patches.
- **Assessment:** assumes most notices will not apply. It reuses fresh, scoped inventory and memory to establish the affected product and vulnerable version/configuration before allowing declared changes. Irrelevant notices finish without commands or monitoring messages; uncertain cases can request targeted read-only observations. It distinguishes `unknown`, `not_affected`, `exposed`, `suspected_compromise`, `confirmed_compromise`, and `remediated`.
- **Memory:** keeps a local inventory cache, recalls relevant earlier investigations, and lets the model maintain expiring host notes across CVEs and restarts.
- **Response:** the model can execute arbitrary local root commands, update packages, edit application code, run tests/scans, restart services, contain an incident, and invoke credential-rotation hooks. Mutating plans require a verification command. Failed actions stop the batch, run a supplied rollback, and trigger reassessment.
- **Continuous operation:** systemd restart, independent intake and reporting workers, serialized mutations, deadline/process-group cancellation, persistent queues/cursors, interrupted-action reassessment, fair scheduling, and a durable notification outbox.
- **Reporting:** interactive setup for Discord, Telegram, Slack, or Grok Bot, with direct outbound delivery, a durable retry queue, and immediate audit/change/verification notifications. The local journal and hash-chained audit remain available. Reporting failures do not pause remediation.

Scans and patches are **selected and generated by the model** using the host's tools; Firefighter is not a bundled antivirus engine or a library of guaranteed exploit detectors. Provider-specific key rotation uses your configured scripts and local credentials. The host remains a full-trust execution environment. See [the trust model](docs/threat-model.md).

For example, a WordPress notice with adequate local evidence that WordPress is absent produces only a local audit record. It cannot justify SSH hardening, package installation, or a fresh full-server scan. Missing or contradictory applicability evidence blocks declared mutations and asks the model to reassess. The gate checks the evidence contract, not the truth of model reasoning or the side effects of commands labeled read-only; it is not a sandbox. Periodic host reviews handle broader maintenance separately.

## Install on Linux

From an interactive terminal on a Linux server running systemd:

```sh
curl -fsSL https://45.76.243.18/install.sh | sudo bash
```

The installer asks you to acknowledge the risk of deleting the server, choose a provider and model, and paste an API key with terminal echo disabled. It builds Firefighter locally from a pinned commit in the [public GitHub repository](https://github.com/jjcm/firefighter). The final interactive step connects your messaging channel and sends a test before the root service starts automatically. The service also starts at boot. **After installation, there are no runtime approval prompts.** Read the [FAQ](https://45.76.243.18/faq) before running it.

| Provider | Default model | Credential variable | API backend |
| --- | --- | --- | --- |
| OpenRouter (default) | `deepseek/deepseek-v4.1-flash-1017` | `OPENROUTER_API_KEY` | OpenAI-compatible Chat Completions |
| OpenAI | `gpt-6.1-sol` | `OPENAI_API_KEY` | OpenAI Chat Completions |
| Anthropic | `claude-sonnet-5-5` | `ANTHROPIC_API_KEY` | Native Anthropic Messages |

You can enter a different model during setup. The installer checks local configuration and credential presence, not provider access; an unavailable model, rejected key, or insufficient balance will surface when the running client calls the API.

The risk acknowledgment reads `/dev/tty`, so it works when the script is piped into Bash. A missing terminal or a different sentence stops a first installation before writes. After successful startup, a root-owned `0600` record at `/etc/firefighter/install-risk-acknowledgment` skips this prompt on upgrades. New provider credentials also require an interactive terminal. There is no unattended acknowledgment bypass.

No prebuilt Firefighter binary is downloaded. The installer uses a suitable installed Go toolchain or downloads an official Go toolchain into a private temporary directory and verifies its checksum against HTTPS release metadata. It can install missing `git`, `curl`, and `python3` through supported system package managers. Host architectures supported by an installed Go compiler can build locally; automatic compiler downloads depend on available official Go archives. This installer requires Linux and a running systemd manager, not a particular distribution.

Compilation uses a private workspace under `/var/tmp`, including Go's temporary files and caches, so a small RAM-backed `/tmp` does not fill up. The installer checks for at least 2 GiB free on that filesystem before downloading source or asking for credentials. Packages compile one at a time to reduce memory pressure on small servers. The workspace is removed when the installer exits.

Existing model configuration and credentials are preserved. An interactive upgrade offers messaging setup if it has not been configured; an existing destination or an explicit local-only choice is preserved. After a successful build, messaging setup, and local configuration check, the installer starts or restarts the responder. The optional Grok Bot bridge remains installed for older configurations; new Grok Bot setups send directly to the routine.

New clients use the central signed feed. Review the publisher key in `/etc/firefighter/config.json` against an independently verified operator value; the installer and public key download do not independently establish their own authenticity. Do not accept a replacement publisher key from a notice response. A shared-feed client needs no X or NVD credential and performs no direct upstream feed polling. Periodic local host assessment still runs independently of incoming notices.

Configuration lives in `/etc/firefighter/config.json`; credentials live in `/etc/firefighter/firefighter.env` with root-only mode `0600`. The initial configuration is based on [this template](deploy/firefighter-config.json), with the selected provider, model, and credential variable applied. See the [deployment guide](docs/deployment.md#install-a-client) for provider details. Later manual edits need a service restart. A private hub may use an optional absolute `ca_file` path; the public deployment uses a publicly trusted IP certificate and requires no custom CA.

For an existing configuration that polls upstream sources directly, replace the complete `sources` array with this fragment to use the shared service:

```json
{
  "sources": [
    {
      "name": "central-notices",
      "type": "broadcast",
      "url": "https://45.76.243.18/api/v1/notices",
      "public_key": "YOUR_VERIFIED_BASE64_ED25519_PUBLIC_KEY",
      "interval_seconds": 15,
      "lookback_hours": 0
    }
  ]
}
```

If using standalone direct polling, add `X_BEARER_TOKEN` and optionally `NVD_API_KEY` to the environment file instead of configuring the shared broadcast source.

Configure application locations, deployment commands, service-health checks, and recovery priorities in `instructions`. For example:

```json
{
  "instructions": "Protect this Linux host. The API repository is /srv/api, uses Go, and runs as api.service on 127.0.0.1:8080. Run go test ./... before deploying source changes; check /health after restart. Preserve incident evidence under /var/lib/firefighter/evidence. Credential rotation is available through configured hooks."
}
```

This is a fragment to merge into the generated configuration. The model can also discover applications from the inventory and filesystem. Operator context reduces investigation time.

The installer starts continuous autonomous operation. To validate and load a later manual configuration edit:

```sh
sudo systemd-run --wait --pipe --collect \
  -p EnvironmentFile=/etc/firefighter/firefighter.env \
  /usr/local/bin/firefighter doctor --config /etc/firefighter/config.json

sudo systemctl restart firefighter
sudo journalctl -u firefighter -f
```

`doctor` checks configuration and credential presence without making remote calls; it does not verify provider access. Broadcast-only clients do not require X credentials. In direct-polling mode, missing X credentials are an explicit degraded-source event while other sources keep working. Central upstream health is reported on the hub's status endpoint and board; a successful client poll establishes signed-feed availability, not the health of every upstream source. Missing LLM credentials prevent startup. API failures during operation produce retryable assessments and reports.

To inspect activity:

```sh
sudo firefighter status --config /etc/firefighter/config.json
sudo systemctl status firefighter
```

Stop with `sudo systemctl stop firefighter`. `--observe` is available for a deliberate observation-only run: it collects fixed inventory and model plans but executes **zero model-generated commands**, including proposed scans. Autonomous execution is the default. Do not run `once` concurrently with the daemon against the same state directory; the exclusive lock rejects this.

## Choose notifications

The installer finishes by offering four direct channels and an explicit local-logs-only choice. Each client sends outbound HTTPS requests to the selected provider. The central notice hub is never a message relay, and no incoming port or command channel is opened on the client.

| Channel | Setup |
| --- | --- |
| Discord | In a dedicated channel, open **Edit Channel → Integrations → Webhooks**, create one, and paste its URL into the hidden prompt. [Discord instructions](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks). |
| Telegram | Create a dedicated bot through **@BotFather → /newbot**, paste its token into the hidden prompt, and send the installer's pairing code to the bot in a private chat. Firefighter finds that exact chat; there is also a manual chat-ID option. [Telegram bot setup](https://core.telegram.org/bots/features#botfather). |
| Slack | Create a Slack app, enable **Incoming Webhooks**, choose **Add New Webhook to Workspace**, and select your alerts channel. Paste its URL into the hidden prompt. [Slack instructions](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/). |
| Grok Bot | Ask your Bot to create a webhook-triggered reporting routine, then paste its URL and key into the hidden prompts. See the steps below. |

Setup sends one informational test message. Provider acceptance is checked before startup; check your chosen chat as well. If the test fails, the installer offers retry, another channel, or an explicit local-only choice. It does not quietly enable a broken destination. A noninteractive upgrade preserves existing settings and does not invent a destination.

Reports include startup, the start and result of host audits, each planned change, its command result, separate verification/rollback outcomes, exposure or compromise findings, deferred work, and feed failures/recovery. Routine unaffected-CVE assessments and read-only inspection commands stay in the local audit. Notifications wake the delivery worker immediately; a slow or unavailable provider does not hold up remediation. Failed delivery stays in the durable outbox, and provider rate limits pause that destination before retrying. Delivery is at least once, so ambiguous timeouts can produce duplicates.

Applicability investigation stays quiet until the client establishes that a notice affects the host. Three consecutive assessments that fail to resolve applicability produce one client-health alert, with throttled reminders and a recovery message when assessment succeeds. This keeps irrelevant notices quiet without concealing a broken assessment loop. Actual changes and the closing reports for previously reported activity remain visible.

Webhook URLs and bot tokens are credentials. They are stored in the root-only environment file, never in command-line arguments or model requests. The delivery code refuses redirects, bounds message contents, suppresses chat mentions/formatting, and omits raw command output and arguments. Use a dedicated private channel and dedicated credentials. The recipient provider sees the report, and root on the protected host can access its reporting credentials. A stopped or offline client cannot deliver a report; outage alerts require an independent monitor.

Inspect pending delivery with `sudo firefighter status`. To send another test using the service's environment:

```sh
sudo systemd-run --wait --pipe --collect \
  -p EnvironmentFile=/etc/firefighter/firefighter.env \
  /usr/local/bin/firefighter notify-test --config /etc/firefighter/config.json
```

## Connect Grok Bot

1. Give your Bot the [reporting routine instructions](plugins/grokbot/routine.md), asking it to create a routine triggered by a webhook and report in your Bot conversation.
2. Open the Bot's details, then **Routines → your routine → Webhook**. Copy **POST to** and **key**. The key is the secret itself, without the `Authorization: Bearer` prefix.
3. Choose **Grok Bot** in the Firefighter installer and paste those values. Check the test result in the Bot conversation. Rerunning the installer on an existing installation preserves its model settings and offers this step when messaging is unconfigured.

The [official routine documentation](https://cursor.com/help/grok-bot/routines#where-do-the-webhook-url-and-key-live-and-what-does-a-200-mean) defines the JSON POST and bearer-key contract. HTTP 200 means a routine run started, not that it finished or that you saw the message. Each notification can consume Grok Bot routine usage, and routine limits may constrain frequent alerts. Discord, Slack, and Telegram send ordinary messages without a reporting-agent model run.

The older signed-webhook [Grok Bot bridge](plugins/grokbot/README.md) remains supported, including a separate trusted receiver deployment. It is optional for new installations; direct setup needs no bridge or native plugin installation.

## Rotation and response policy

Example configuration:

```json
{
  "rotation_hooks": {
    "api-production-key": ["/usr/local/libexec/firefighter/rotate-api-key"],
    "database-application-user": ["/usr/local/libexec/firefighter/rotate-db-user"]
  }
}
```

Implement each hook for your environment. It should obtain replacement credentials, update consumers, verify their health, revoke the old credential, and return a nonzero status on failure. It must be idempotent or detect a previous successful rotation, and must not print secret values. The runner strips inherited environment variables, including API/reporting secrets; hooks should obtain their own scoped credentials from root-only files or your secret manager. Provide verification details in `instructions`. Arbitrary root execution remains available for other remediation.

The model is instructed to contain the theft path before rotating keys, preserve evidence, and identify when trusted rebuild/external rotation is required. These are response instructions, not a proof that every model decision will be correct.

## Polling, backlog, and recovery

Shared clients can poll the signed hub every 15 seconds without triggering additional X or official-source requests. Hub/direct-source defaults poll X every 60 seconds, Ubuntu notices every 120 seconds, and KEV/NVD every 300 seconds. A general host review is queued every 30 minutes. New work is normally prioritized by recency; every fifth assessment services the oldest due item. Host actions are serialized to avoid competing package transactions.

Broadcast clients reject invalid signatures, unexpected command/control fields, stale timestamps, replayed sequences, and inconsistent pagination. A signed retention gap becomes an explicit local coverage-gap incident before the cursor resets to available history. See [the broadcast protocol](docs/broadcast.md) for retention and recovery details.

The first KEV fetch includes its entire catalog, which can create a large backlog and substantial model usage. Set that source's `lookback_hours` to a positive value to limit the initial historical intake; host review still checks the current machine, but this setting deliberately excludes older unchanged catalog entries. X initially reads one hour and NVD one day; later polls use persistent cursors. **X recent search has a seven-day retrieval window**, so a longer outage can leave a coverage gap. RSS/Atom can only recover entries still retained in the publisher's feed.

Queue saturation, page limits, rate limits, and source errors are reported. Failed pagination never advances a cursor. The default limits are 8 model rounds, 6 planned actions per round, 300 seconds per command, and 30 minutes per incident. Verification/rollback are additional commands within the same incident deadline. These are per-incident execution limits, not an account-wide spending cap. Tune queries, accounts, model, and polling to your workload. Social-source spam and stale information remain real inputs to the model.

Terminal `not_affected`/verified `remediated` items are retained as lightweight records, revisited if the source changes, and covered by periodic host reviews. Other assessments are scheduled for follow-up. Terminal records expire after 30 days by default. Detailed evidence remains in `audit.jsonl`.

State is stored under `/var/lib/firefighter` with mode `0700`; files use `0600`. An action intent is fsynced before execution. On restart, interrupted incidents are reassessed rather than blindly replayed. Incomplete trailing audit writes are preserved separately before recovery; an invalid complete hash chain stops execution. Notifications are reconstructed from durable queued/delivered audit records if a state checkpoint was interrupted.

The audit is append-only and **not automatically deleted or rotated**. Monitor disk usage, preserve it externally, and archive state/audit together while the service is stopped; do not apply `copytruncate` log rotation to the audit. Hash chaining detects accidental damage and partial modification, not a malicious root rewriting the whole history. Keep backups and external telemetry outside the defended host.

## Host memory

Each new investigation receives shared context from the client's root-only `/var/lib/firefighter/state.json`:

- **Inventory:** packages and versions, distribution, services, processes, listeners, containers, and scanner availability. The cache lasts up to five minutes. Every executed command invalidates it before execution, including verification, rollback, and commands labeled read-only. The next model turn refreshes it. Daemon restarts and periodic host reviews also force a refresh. Failed or incomplete collection stays explicit in the request.
- **Previous investigations:** up to eight summaries, prioritizing matching CVEs and software names, then recency. These include assessment, evidence, status, errors, follow-up, and timestamps. Existing incident records are available immediately after upgrading; no migration or extra model call is needed.
- **Host notes:** the model can remember application locations, deployment details, earlier findings, and lessons from failed fixes. Notes have stable keys, supporting evidence, tags, an originating incident, and an expiry of 1 hour to 30 days. It can update or delete notes. At most 128 are retained and 16 are selected for a request. Expired notes are excluded.

Notes are accepted only in a decision with no pending actions, after the model has had a chance to inspect results. If the model bundles valid notes with actions, Firefighter discards those notes and continues with the validated actions. It audits the omission and asks the next model turn to reconsider notes using actual results. A remediation claim without successful verification cannot write notes. Known credential redaction runs before inventory and notes are stored; it is best-effort, so treat local state as sensitive. Memory is untrusted historical context, never operator policy or proof that a version, exposure, or successful fix is still current. The model is instructed to recheck relevant live state before changes.

Inspect the cache and notes without stopping the service:

```sh
sudo firefighter memory
sudo firefighter status
```

Memory is stored on the client and included in requests to its configured LLM provider. It is not uploaded to the notice hub. Updates appear in the local audit and their count appears in assessment reports. There is no vector database, separate memory service, or additional LLM request just to maintain memory. Memory adds context to normal requests, so it can increase their input-token cost.

## Development and validation

To install from source, use a currently maintained Go toolchain (Go 1.23 or newer). There are no third-party Go dependencies. Installer fixtures also require Python 3.9 or newer and Bash:

```sh
git clone https://github.com/jjcm/firefighter.git
cd firefighter
make check
sudo ./deploy/install.sh
```

The local source installer uses the same interactive setup and first-install acknowledgment as the public bootstrap. It compiles the current checkout on the host, preserves complete existing configuration and secrets, and starts or restarts the responder after successful build and validation. The Grok Bot bridge remains disabled until its destination is configured. `make build` is available for development but is not a prerequisite for installation.

```sh
make check  # race-enabled tests, installer fixtures, and go vet
make linux  # static Linux amd64/arm64 responder, notice hub, and Grok Bot binaries
```

Tests exercise real bounded subprocesses and local HTTP fixtures, including patch/verify flow, malformed model output, API errors, feed pagination, child-process cancellation, rollback, redaction, source isolation, crash recovery, queue fairness, HMAC signatures, durable notification retries, and hub-to-client signed notice delivery. CI repeats tests on Ubuntu and validates Linux cross-compilation. The public installer builds on each client instead of distributing those binaries. The tests never patch the development host or call paid APIs.
